#### Обоснование архитектурного выбора:

- Централизация управления ставками: позволяет избавиться от устаревших Excel-файлов, повысить прозрачность и надёжность.
- Разделение интерфейсов по потребителям:
    - REST API для внутренней системы кол-центра.
    - CSV-выгрузка для ограниченных возможностей внешнего партнёра.
- Минимальные изменения в существующих системах:
    - Основной кол-центр уже использует стек React + Spring Boot, что упрощает интеграцию.
    - Выгрузка файлов может быть реализована с использованием планировщика (например, cron, Task Scheduler) и не требует сложной интеграции.
- Совместимость со стеками и экспертизой банка: используются MS SQL, React, Java — всё это уже поддерживается внутри команды.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

| Альтернатива                                                 | Недостатки                                                                                                |
|--------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------|
| Продолжать использовать Excel-файлы                          | Нет контроля версий, невозможно интегрировать с ИТ-системами, высокий риск ошибок и ручного труда         |
| REST API для партнёрского кол-центра                         | У партнёра нет инфраструктуры для REST-интеграции, возможна только работа с файлами                       |
| Ручная передача ставок операторам                            | Высокая нагрузка на персонал, задержки, ошибки, неэффективность                                           |
| Реализация единого общего веб-интерфейса для всех операторов | Потребуется дополнительная авторизация, техническая поддержка, обучение партнёров, сложная инфраструктура |


### Недостатки, ограничения, риски

- Человеческий фактор:
    - Обновление ставок вручную — возможны ошибки или забывчивость.
- Передача CSV-файлов:
    - При использовании email или SFTP необходимо обеспечить безопасность (шифрование, контроль доступа).
    - Возможны сбои в передаче и нарушенная синхронизация.
- Риски рассинхронизации:
    - При параллельном использовании API и выгрузки нужно обеспечить единый источник данных.
- Нагрузка на эксплуатацию:
    - Появление новых процессов требует настройки мониторинга, логирования, оповещений при сбоях выгрузки.
